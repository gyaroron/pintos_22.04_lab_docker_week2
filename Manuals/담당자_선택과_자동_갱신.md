# 담당자 선택과 자동 갱신

팀 저장소: [PintOS Week2](https://github.com/gyaroron/pintos_22.04_lab_docker_week2)

## 배정은 사용자가 결정한다

모든 Issue·Sub-issue의 주 담당자·리뷰어는 사용자가 정하기 전 공란이다. 자동화는 작업을 분배하지 않는다. 사용자가 선택한 실제 GitHub Assignees를 본문과 상위 표에 표시하는 역할만 한다. 리뷰어 선택·리뷰 요청·Project 상태 변경·브랜치 생성·커밋 생성은 하지 않는다.

## 같은 상위 Issue를 두 사람이 나눠 맡을 때

1. 공통 상위 Issue에서 필요한 Sub-issue와 선행 관계를 확인한다.
2. 맡기로 결정한 Sub-issue를 연다.
3. 오른쪽 **Assignees → 톱니바퀴 → 본인 계정 선택**으로 실제 담당자를 지정한다.
4. Actions의 **Sync issue role display** 실행 결과를 확인한다.
5. 해당 Sub-issue 본문의 `주 담당자`와 상위 Issue 표의 해당 행에 같은 계정이 표시되는지 확인한다.
6. 상대방도 자신이 맡기로 결정한 다른 Sub-issue에서 같은 절차를 수행한다.

Issue #1 아래 #2·#3이라는 관계와 브랜치 이름은 담당자 선택과 독립적이다. 누가 #2 또는 #3을 맡을지는 이 문서나 자동화가 정하지 않는다. 상위 Issue에 담당자를 지정해도 자식들에게 자동 배정하지 않으며, 자식 담당자를 지정해도 상위 자체의 담당자를 바꾸지 않는다.

## 담당 해제

Assignees에서 선택된 계정을 해제한다. 모두 해제하면 본문은 `- 주 담당자:`로, 상위 표의 해당 담당자 칸은 공란으로 돌아간다. 리뷰어는 그대로 유지한다. 여러 Assignees를 직접 선택하면 그 계정들을 모두 표시한다.

본문의 `주 담당자`에 계정만 직접 적는 방식은 실제 GitHub 담당자 지정이 아니다. 입력 기준은 오른쪽 Assignees다. 본문을 직접 고쳤다면 Actions에서 수동 재조정을 실행해 실제 지정 상태와 맞출 수 있다.

## 활성화와 수동 재조정

`.github/workflows/issue-role-sync.yml`과 `.github/scripts/sync-issue-roles.cjs`가 **기본 브랜치에 병합된 뒤** 자동 실행된다. PR 브랜치에만 있는 동안에는 이슈에서 담당자를 선택해도 이 자동화는 실행되지 않는다.

기본 브랜치 병합 후 **Actions → Sync issue role display → Run workflow**를 누르면 전체 기존 이슈의 표시를 재조정한다. 자동 이벤트는 `opened`, `assigned`, `unassigned`다. 오류가 있으면 같은 Actions 화면에서 로그를 확인하고 재실행한다. 담당자 변경 직후의 표시는 워크플로 실행이 끝난 뒤 반영된다.

## 보존 범위와 검증

- 실제 Assignees는 자동화가 변경하지 않는다.
- 본문의 주 담당자 줄과 관리되는 상위 표의 해당 담당자 칸만 갱신한다.
- 리뷰어, 요구사항, 테스트 명령, 다른 문장, 코드 블록, 부모·자식 관계, 진행 상태는 보존한다.
- 실제 부모 관계를 API로 확인하고 최신 본문을 다시 읽어 갱신한다. 같은 저장소의 실행은 직렬화하고 매번 전체 현재 상태를 확인한다.
- `contents: read`, `issues: write` 권한의 Actions 기본 토큰을 사용한다. 개인 토큰을 추가로 저장할 필요가 없다.
- 검증 명령은 `node .github/scripts/tests/sync-issue-roles.test.cjs`다. 테스트는 가짜 데이터로 담당 지정·해제, 형제 보존, 코드 블록 보존, 반복 실행, 누락 이벤트 보완을 확인한다. 실제 이슈에 임의의 담당자를 지정하지 않는다.
