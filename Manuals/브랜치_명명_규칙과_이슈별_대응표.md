# 브랜치 명명 규칙과 이슈별 대응표

대상: [PintOS Week2 팀 저장소](https://github.com/gyaroron/pintos_22.04_lab_docker_week2) · 기준일: 2026-10-16

## 공통 규칙

같은 상위 작업은 하나의 Issue로 관리하고, 두 작업자는 그 Issue의 서로 다른 Sub-issue를 맡는다. 실제 작업 브랜치는 Sub-issue별로 만들며 같은 상위 Issue의 설명형 접두부를 공유한다.

```text
feature/issue-<상위번호>-<공통작업>/sub-<하위번호>-<세부작업>
```

- `issue-<상위번호>-<공통작업>`: 상위 Issue의 GitHub 번호와 공통 작업 이름이다. 현재 공통 작업 이름은 상위 제목의 `.c`를 제거한 테스트명이다.
- `sub-<하위번호>-<세부작업>`: 담당 Sub-issue의 GitHub 번호와 실제 작업 내용을 드러내는 이름이다. 하위 번호는 부모 안의 순서가 아닌 저장소 전체 이슈 번호다.
- 영문 소문자·숫자·하이픈을 사용한다. 단독 Sub-issue는 테스트명을 사용하고, 여러 Sub-issue로 나뉜 경우에는 각 책임을 구별하는 설명을 붙인다.
- 같은 부모 아래의 브랜치는 앞부분이 같고 뒷부분은 다르다. 상위 Issue 번호만으로 하나의 공유 구현 브랜치를 만들지는 않는다.
- 작업을 시작할 때 최신 팀 `upstream/main`에서 생성하고 본인의 `origin`에 push한다. 저장소 소유자와 fork 작업자 모두 같은 이름 규칙을 사용한다.
- 이 문서의 접두부는 이름의 공통 부분이다. 접두부 자체를 별도 브랜치로 생성하지 않는다.

```text
Issue #1 · args.c
├─ Sub-issue #2 → feature/issue-1-args/sub-2-args-none
└─ Sub-issue #3 → feature/issue-1-args/sub-3-args-single-multiple
```

## Issue 연결과 PR

브랜치에 이슈 번호를 적는 것만으로 GitHub의 부모·자식 관계나 PR 연결이 자동 생성되지는 않는다. 기존 native Sub-issue 관계를 유지하고 PR 본문에 실제 번호를 명시한다.

```text
Refs #<상위번호>
Closes #<하위번호>
```

상위 Issue #1 아래 Sub-issue #2의 예는 `Refs #1`, `Closes #2`다. `Closes #1`로 공통 상위 작업을 조기에 닫지 않는다. PR의 base는 팀 저장소 `main`이며 GitHub의 기본 브랜치로 병합될 때 하위 이슈 자동 닫기가 적용된다. 상위 Issue는 전체 하위 작업의 완료·검증을 확인한 뒤 정리한다.

이름 변경은 담당자·요구사항·공식 테스트 명령·Project 상태를 바꾸지 않는다. 이미 진행 중인 브랜치는 자동으로 개명되지 않는다. 기존 브랜치나 PR이 있다면 연결 상태를 먼저 확인하고 처리하며, 이 대응표만으로 원격 브랜치 삭제나 강제 push를 수행하지 않는다.
